# Equality Design System

Equality is the design system for all EQTY Lab projects. It is a monorepo composed of packages available under `packages`.

The "demo" package is the Astro documentation site. Each component has a corresponding MDX docs page under `packages/demo/src/content/docs/components`.

The "docs" package (`@eqtylab/docs`) is the Astro documentation framework the "demo" site is built with.

The "tokens" package contains a design tokens formatted JSON file which is generated using Bjango's Pinwheel app. Tokens should always be added with Pinwheel and exported to JSON. Tokens are automatically built to CSS by the "ui" package's `build:tokens` script, which `pnpm build` runs; `pnpm dev` rebuilds them whenever the JSON changes.

The "ui" package contains our React components located under `ui/src/components/`. Its tests live in `packages/ui/tests`.

The "skills" package contains agent skills we publish to other repos via `npx skills add eqtylab/equality`, so that teams building applications always build with Equality instead of reinventing it. See `packages/skills/README.md`.

The docs site serves an agent-readable Markdown twin of every page: `/llms.txt` indexes every page with its description, and `/components/<slug>.md` is the full page. Both are generated by routes in `packages/docs/src/runtime/routes` (`llms-txt.ts` and `docs-md.ts`) — nothing to regenerate by hand.

## Development

Run `pnpm install` to get dependencies, `pnpm build` in the repo root to render the design tokens to CSS and build every package, and `pnpm dev` to start the dev server. Run `pnpm test` to run every package's tests.

## Guidance

- Always reference the `create-documentation` skill when interacting with component documentation MDX files.
- Always reference the `create-component` skill when creating a new component, or making changes in usability to an existing component.
- A component's docs page `description` is how agents in other repos find it: the `equality-design-system` skill sends them to `/llms.txt`, which lists each page by its description alone. Write it in the words someone looking for the component would use. A compound part or feature without its own page, such as `TableRowAction` on the Table page, goes in its page's description, or nothing points to it.
- Add a row to the name translation table in `packages/skills/equality-design-system/SKILL.md` only when a clear description won't prevent a mix-up: when people know the component by another name (a combobox is `Select` with `SelectSearch`), or when another Equality component or composition looks like the right tool and isn't (`Dialog` with two buttons instead of `AlertDialog`). Every agent reads the whole table on every task, so a row for something whose name and description already say what it is only makes the confusions harder to spot.
- Strive to create accessible components that will function with keyboard navigation, screen reader usage, and accessible markup in mind. Alert the developer if they are specifically requesting that you implement something that won't be accessible.
- Do not over-comment the code. Comments should be added to warn others of very negative things that will happen if you change code. Comments should NOT be added for the sake of describing what code does.
